# CFMS ページ詳細仕様書

## 0. 書き方・共通ルール

- ページ名は「日本語名 (`PageName`)」の形式で記述する。
- 各ページについて、目的、構成要素、操作、REST API、入力・出力、エラー条件を記述する。
- 入力項目の `*` は必須項目を示す。
- APIの認証状態・権限チェックはサーバー側で必ず実施する。画面上でボタンを隠すことだけを権限制御の根拠にしない。
- APIのリクエスト／レスポンス形式は論理仕様であり、実装時には共通レスポンス形式に統一してよい。
- `userId` は `Users.id`（AUTO_INCREMENT）を表す。表示用の識別子であり、これだけで認証してはならない。
- `token` はユーザー生成時に発行し、アカウント終了まで固定する。QRコードには `userId` ではなく `token` を含める。画面には `userId` と `token` の文字列表記を表示する。
- QRコードから取得した `token` はサーバーで照合し、ユーザーを特定する。
- `Scores` は1プレーにつき1レコードを登録する。`score` にはそのプレーで獲得した合計ポイントを保存する。
- 同一ユーザーが同一ブースを利用できる回数は環境変数で制御する。初期運用値は3回とし、付与ポイント数そのものに上限は設けない。
- 景品交換時はポイント消費履歴を記録せず、スタッフがユーザーを無効化する。無効化後は得点付与などの操作を受け付けない。
- 今回は在庫管理、操作監査ログ、システム設定ページ、ポイント消費履歴を実装対象外とする。

## 1. 管理者・スタッフ用ログインページ (`StaffLoginPage`)

### 目的
管理者およびスタッフがスタッフIDとパスワードを用いてログインする。

### 構成要素
- システムタイトル（CFMS）
- スタッフID入力欄
- パスワード入力欄
- ログインボタン
- エラーメッセージ表示領域

### 操作
1. スタッフIDとパスワードを入力する。
2. ログインボタンを押す。
3. 認証成功時はセッションを確立し、担当可能な店舗の選択へ進む。担当店舗が1つの場合に自動選択するかどうかは実装時に統一する。
4. 認証失敗時はエラーメッセージを表示する。

### REST API

#### `POST /api/staff/login`
スタッフ認証を行う。

**入力**
- `*staffId`: スタッフID
- `*password`: パスワード
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `message`: 失敗理由（必要に応じて）

**エラー条件**
- スタッフIDまたはパスワードが不正
- アカウントが利用できない
- CSRF検証失敗

#### `POST /api/staff/isLoggedIn`
現在のスタッフセッションを確認する。

**入力**
- なし（セッションを使用）

**出力**
- `success`: 成否
- `isLoggedIn`: ログイン状態
- `staff`: ログイン中のスタッフ情報（認証済みの場合）

## 2. ユーザー再ログインページ (`UserLoginPage`)

### 目的
セッション切れや端末変更時に、ユーザーIDとパスコードで再ログインする。

### 構成要素
- ユーザーID入力欄
- パスコード入力欄
- ログインボタン
- エラーメッセージ表示領域

### 操作
1. ユーザーIDとパスコードを入力する。
2. ログインボタンを押す。
3. 認証成功時はユーザーセッションを確立し、ユーザーメインページへ遷移する。

### REST API

#### `POST /api/user/login`
**入力**
- `*userId`: `Users.id`
- `*passcode`: 発行済みパスコード
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `message`: 失敗理由（必要に応じて）

**エラー条件**
- ユーザーIDまたはパスコードが不正
- パスコードが未発行（DB上で `null`）
- アカウントが終了済み
- CSRF検証失敗

#### `POST /api/user/isLoggedIn`
**入力**
- なし（セッションを使用）

**出力**
- `success`: 成否
- `isLoggedIn`: ログイン状態

> QRコードに含まれる固定トークンは、スタッフによるユーザー特定・アクティベート・得点付与に使用する。ユーザーの再ログイン画面では、既存方針どおりIDとパスコードを使用する。

## 3. ユーザーメインページ (`UserMainPage`)

### 目的
ユーザーアカウントを生成し、ユーザーID、QRコード、ポイント残高、ポイント獲得履歴、アカウント状態を表示する。

### 構成要素
- アカウント状態（未アクティベート／有効／終了）
- ユーザーID表示
- トークン文字列表示
- トークンを格納したQRコード表示
- 現在の獲得ポイント合計
- ポイント獲得履歴（日時、ブース、獲得ポイント）
- 必要に応じて再ログインへの導線

### 操作
1. 未生成のセッションでページを開いた場合、ユーザーを生成する。
2. 生成後、ユーザーIDとトークンを表示し、トークンをQRコード化する。
3. 既にユーザーが生成されている場合は、重複生成せず既存ユーザー情報を表示する。
4. アカウント終了済みの場合は終了状態を表示し、QRコードを利用した得点付与ができないことを案内する。

### REST API

#### `POST /api/user/generate`
ユーザーを生成する。重複リクエストでユーザーが複数作成されないようにする。

**入力**
- なし（セッションを使用）

**出力**
- `success`: 成否
- `userId`: 生成された `Users.id`
- `token`: 生成された固定トークン
- `isActive`: アクティベート状態

#### `GET /api/user/info`
ログイン中ユーザーの情報を取得する。

**入力**
- なし（セッションからユーザーを特定）

**出力**
- `success`: 成否
- `userId`: `Users.id`
- `scores`: ポイント獲得履歴の配列
  - `scoreId`: 得点レコードID
  - `score`: 1プレーで獲得した合計ポイント
  - `storeId`: ブースID
  - `storeName`: ブース名
  - `createdAt`: 登録日時
- `totalScore`: `scores` の合計
- `isActive`: アクティベート状態
- `finishedAt`: 終了時刻（未終了の場合は `null`）

#### `POST /api/user/heartbeat`
ユーザーセッションの生存を定期報告する。

**入力**
- なし（1分に1回自動送信）

**出力**
- `success`: 成否

**補足**
- ハートビートが5分以上途絶えた、アクティベート済みかつ未終了のユーザーは、管理者向けの無応答一覧に表示する。
- 今回は専用の監査ログ機能は実装しない。

## 4. 管理者・スタッフ用メインページ (`StaffMainPage`)

### 目的
ログイン中のスタッフの権限と担当店舗に応じた機能メニューを表示する。

### 構成要素
- ログイン中のスタッフ名・権限
- 現在選択中の担当店舗
- 担当店舗の選択UI（複数店舗に所属する場合）
- ログアウトボタン
- 権限に応じた機能メニュー

### 操作
- スタッフはログイン後、所属店舗の中から操作対象店舗を選択する。
- 選択できる店舗は、スタッフと店舗の中間テーブルで紐付いた店舗に限る。
- 管理者は全機能にアクセスできる。
- 受付スタッフはユーザー生成・アクティベート、店舗スタッフは担当店舗での得点付与、景品担当スタッフはユーザー終了処理を行う。
- ログアウト時はスタッフセッションを破棄する。

### REST API

#### `GET /api/staff/menu`
**入力**
- なし（セッションを使用）

**出力**
- `success`: 成否
- `accessiblePages`: アクセス可能なページ一覧
- `staff`: スタッフ情報（ID、名前、権限）
- `selectedStore`: 選択中の店舗（選択済みの場合）

#### `GET /api/staff/stores`
ログイン中スタッフが担当可能な店舗一覧を取得する。

**入力**
- なし

**出力**
- `success`: 成否
- `stores`: 店舗ID・店舗名の配列

#### `POST /api/staff/selectStore`
操作対象店舗を選択する。

**入力**
- `*storeId`: 選択する店舗ID
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `selectedStore`: 選択した店舗情報

**エラー条件**
- スタッフが所属していない店舗を選択した
- 店舗IDが存在しない

#### `POST /api/staff/logout`
スタッフセッションを終了する。

**入力**
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否

## 5. 受付アカウント有効化ページ (`ActivatePage`)

### 目的
受付スタッフが料金支払いを確認した後、ユーザーをアクティベートする。

### 構成要素
- QRコードリーダー起動ボタン
- 読み取ったトークン入力欄（必要に応じて手動入力可能）
- 対象ユーザーID表示
- アカウント状態表示
- アクティベートボタン
- 処理結果・エラー表示

### 操作
1. ユーザーのQRコードを読み取る。
2. QRコードから得たトークンでユーザーを特定する。
3. 対象ユーザーが未アクティベートであることを確認する。
4. 受付スタッフがアクティベートを実行する。
5. 成功時は有効状態を表示する。

### REST API

#### `POST /api/user/activate`
**入力**
- `*token`: QRコードから読み取ったトークン
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `userId`: 対象ユーザーID
- `isActive`: 更新後のアクティベート状態
- `message`: 結果メッセージ

**エラー条件**
- トークンに対応するユーザーが存在しない
- 既にアクティベート済み
- アカウント終了済み
- 受付権限がない

## 6. 得点登録ページ (`ScoreRegistrationPage`)

### 目的
店舗スタッフがQRコードを読み取り、ゲーム1プレー分の合計ポイントをユーザーに登録する。1プレーにつき1回の得点登録処理を行う。

### 構成要素
- QRコードリーダー起動ボタン
- 読み取ったトークンの対象ユーザー情報
- ユーザーID・アカウント状態表示
- 現在の獲得ポイント合計
- 当該ブースでの利用回数／利用可能回数
- 1プレー分の合計ポイント入力欄
- 得点登録ボタン
- 結果・エラーメッセージ表示

### 操作
1. ログイン中スタッフが担当店舗を選択していることを確認する。
2. ユーザーのQRコードを読み取る。
3. トークンからユーザーを特定し、アカウント状態と当該店舗での利用回数を取得する。
4. 1プレーで獲得したポイント合計を入力し、登録する。
5. サーバーはアクティベート済み・未終了であること、担当店舗が許可されていること、当該店舗の利用回数が上限未満であることを検証する。
6. 成功時、`Scores` に1レコードを追加する。利用回数上限は環境変数で設定し、運用上の初期値は3回とする。
7. ポイント付与数そのものの上限は設けない。

### REST API

#### `POST /api/score/get`
対象ユーザーのポイント履歴と、選択中店舗での利用回数を取得する。

**入力**
- `*token`: QRコードから読み取ったトークン

**出力**
- `success`: 成否
- `user`: ユーザーID、アクティベート状態、終了状態
- `totalScore`: 獲得ポイント合計
- `scores`: 得点履歴配列（得点ID、登録日時、店舗ID・店舗名、ポイント数）
- `storeUsageCount`: 選択中店舗の利用回数
- `storeUsageLimit`: 環境設定上の利用回数上限
- `canAddScore`: 得点登録可能か

#### `POST /api/score/add`
1プレー分の合計ポイントを登録する。

**入力**
- `*token`: QRコードから読み取ったトークン
- `*score`: 1プレー分の合計ポイント
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `message`: 結果またはエラーメッセージ
- `storeUsageCount`: 登録後の当該店舗利用回数

**サーバー側の検証**
- ユーザーが存在する。
- ユーザーがアクティベート済みで、終了していない。
- スタッフに選択中店舗での得点付与権限がある。
- 当該店舗の利用回数が環境変数で設定した上限未満である。
- `score` が仕様上許容される数値である（ポイント上限は設けない）。
- 同時リクエストで上限を超えないよう、利用回数確認と登録を整合性のある処理として行う。

**エラー条件**
- 未アクティベート、または終了済みユーザー
- 不明なトークン
- 店舗未選択、または担当外店舗
- 利用回数上限到達
- 不正なポイント値
- 権限不足

> 1プレーにつき1レコードを作成するため、1プレーのポイントを複数の `Scores` レコードに分割しない。

## 7. スタッフ管理ページ (`StaffManagementPage`)

### 目的
管理者がスタッフアカウント、権限、所属店舗を管理する。

### 構成要素
- スタッフ一覧
- スタッフ新規作成フォーム
- スタッフ名・ID・権限の編集欄
- パスワード設定欄
- 所属店舗の複数選択UI
- 保存・削除ボタン
- 結果・エラーメッセージ

### REST API

#### `GET /api/admin/staffs`
**入力**
- なし

**出力**
- `success`: 成否
- `staffs`: スタッフ一覧（ID、名前、権限、所属店舗ID一覧）

#### `POST /api/admin/staff`
スタッフを新規作成または更新する。

**入力**
- 新規作成時：
  - `*staffId`: スタッフID
  - `*name`: スタッフ名
  - `*password`: パスワード
  - `*role`: 権限
  - `storeIds`: 所属店舗ID配列
- 更新時：
  - `*staffId`: 対象スタッフID
  - `name`: スタッフ名
  - `password`: 指定時のみパスワードを更新
  - `role`: 指定時のみ権限を更新
  - `storeIds`: 指定時のみ所属店舗を更新
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `message`: 結果メッセージ

**補足**
- パスワードはハッシュ化して保存する。
- 権限は受付、店舗、景品担当、管理者を想定する。
- 所属店舗はスタッフと店舗の多対多中間テーブルで管理する。

#### `POST /api/admin/staff/delete`
**入力**
- `*staffId`: 削除対象スタッフID
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否

## 9. 一括得点登録・ユーザー作成ページ (`BulkScoreRegistrationPage`)

### 目的
管理者が紙媒体運用などの特例に対応するため、ユーザーを個別に作成したり、通常のブース利用回数制限を適用せずに得点を登録したりする。

### 構成要素
- ユーザー作成操作
- 対象ユーザーIDまたはトークン入力欄
- 対象店舗選択欄
- ポイント入力欄
- 得点登録ボタン
- 結果・エラーメッセージ

### REST API

#### `POST /api/admin/score/bulkAdd`
管理者権限で得点を登録する。

**入力**
- `*token` または `*userId`: 対象ユーザーの識別情報
- `*storeId`: 対象店舗ID
- `*score`: 登録するポイント
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `message`: 結果メッセージ

**補足**
- 管理者用の例外処理であり、一般スタッフの得点登録とは権限を分離する。
- 本ページの処理がブース利用回数に算入されるかどうかは、実運用ルールに合わせて実装時に統一する。
- 監査ログは今回実装しないため、旧仕様にあった `reason` のログ保存は対象外とする。

## 10. 集計分析ページ (`AnalysisPage`)

### 目的
管理者がユーザー数、アクティベート状況、ブース別の利用状況・得点を確認し、集計データをCSVで出力する。

### 構成要素
- 総ユーザー数
- アクティベート済みユーザー数
- ブース別利用回数ランキング
- ブース別付与ポイント合計ランキング
- CSV出力ボタン
- 無応答ユーザー一覧への表示領域（必要に応じて別画面に分離）

**今回の対象外**
- 売上集計（売上データを保持する仕様が未定義のため）
- ポイント消費合計（消費履歴を記録しないため）
- 景品出庫データ（在庫・出庫管理を行わないため）
- Excel出力（今回はCSV出力を対象とする）

### REST API

#### `GET /api/admin/statistics`
**入力**
- なし

**出力**
- `success`: 成否
- `totalUsers`: 総ユーザー数
- `activeUsers`: アクティベート済みユーザー数
- `finishedUsers`: 終了済みユーザー数
- `ranking`: 店舗別集計配列
  - `storeId`: 店舗ID
  - `storeName`: 店舗名
  - `playCount`: プレイ回数
  - `totalScore`: 付与ポイント合計

#### `GET /api/admin/export`
集計データをCSV形式で出力する。

**入力**
- `*type`: 出力種別（ユーザー履歴、店舗別集計など）

**出力**
- 成功時はCSVファイルデータ、またはダウンロード用レスポンス
- 失敗時はエラー情報

## 11. パスコード発行・無応答ユーザー確認ページ (`PasswordIssuancePage`)

### 目的
受付または管理者がユーザーの再ログイン用パスコードを発行し、ハートビートが途絶えたアクティブユーザーを確認する。

### 構成要素
- ユーザーID入力欄
- パスコード発行ボタン
- 発行されたパスコード表示領域
- 無応答ユーザー一覧（ユーザーID、最後に利用した店舗、最終Heartbeat時刻）
- 結果・エラーメッセージ

### REST API

#### `POST /api/user/issuePasscode`
**入力**
- `*userId`: 対象ユーザーID
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `passcode`: 発行されたパスコード（発行時のみ）

**エラー条件**
- 対象ユーザーが存在しない
- 対象ユーザーが終了済み
- 実行権限がない

#### `GET /api/admin/session/expired`
Heartbeatが5分以上途絶えた、アクティベート済みかつ未終了のユーザー一覧を取得する。

**入力**
- なし

**出力**
- `success`: 成否
- `expiredUsers`: 一覧
  - `userId`: ユーザーID
  - `lastStoreId`: 最後に利用した店舗ID
  - `lastStoreName`: 最後に利用した店舗名
  - `lastHeartbeatAt`: 最終Heartbeat時刻

## 12. ユーザー終了・景品交換ページ (`PrizeExchangePage`)

### 目的
景品担当スタッフがユーザーのQRコードを読み取り、景品交換後にアカウントを終了（無効化）する。ポイント消費履歴や在庫は管理しない。

### 構成要素
- QRコードリーダー起動ボタン
- トークン入力欄（必要に応じて手動入力可能）
- 対象ユーザーID表示
- アクティベート状態・終了状態表示
- 現在の獲得ポイント合計表示（確認用）
- 無効化ボタン
- 処理結果・エラーメッセージ

### 操作
1. 景品担当スタッフがユーザーのQRコードを読み取る。
2. トークンでユーザーを特定し、状態と獲得ポイント合計を表示する。
3. 景品交換を行う。
4. スタッフが無効化ボタンを押す。
5. サーバーがユーザーの終了フラグを更新し、終了時刻を記録する。
6. 終了後は、そのユーザーへの得点付与を拒否する。

### REST API

#### `POST /api/user/lookupByToken`
QRコードのトークンに対応するユーザー情報を取得する。

**入力**
- `*token`: QRコードから読み取ったトークン

**出力**
- `success`: 成否
- `userId`: ユーザーID
- `isActive`: アクティベート状態
- `finishedAt`: 終了時刻（未終了の場合は `null`）
- `totalScore`: 獲得ポイント合計

#### `POST /api/user/finish`
ユーザーアカウントを終了する。

**入力**
- `*token`: QRコードから読み取ったトークン
- `*csrfToken`: CSRFトークン

**出力**
- `success`: 成否
- `finishedAt`: 終了時刻
- `message`: 結果メッセージ

**サーバー側の検証**
- 実行者が景品担当スタッフまたは管理者である。
- トークンが有効である。
- 対象ユーザーが既に終了していない。
- 終了処理は二重実行されても、終了状態や終了時刻を不整合にしない。

## 15. データ定義との対応・実装時の確認事項

### 既存テーブル
- `Users`: `id`, `name`, `is_active`, `finished_at`, `created_at` など
- `Staff`: `id`, `name`, `password`（ハッシュ化）, `role`
- `Stores`: `id`, `name`
- `Scores`: `id`, `user_id`, `staff_id`, `score`, `store_id`, `created_at`

### データ定義書への追加が必要な項目
- `Users.token`: QRコード用の固定・一意なトークン
- `Users.passcode`: パスコード。未発行時は `NULL`
- `Users` のHeartbeat最終受信時刻を永続化する列、または別のセッション管理手段
- スタッフと店舗の多対多中間テーブル（例：`StaffStores(staff_id, store_id)`）
- `Scores` が1プレーにつき1レコードであることを前提に、店舗別利用回数を集計できること

### 実装前に確定する事項
- `Users.name` を利用者が入力するか、自動生成するか。
- `token` の生成方法・長さ・一意性制約。
- パスコードの形式・有効期間・保存方法（平文保存を避ける場合の照合方式）。
- 管理者による一括得点登録がブース利用回数に算入されるか。
- 店舗・スタッフ・ユーザー・得点履歴を削除する場合の参照整合性。
- 「最後に遊んだブース」を得点履歴から取得するか、Heartbeat情報と別に管理するか。
- 売上データを記録しない場合、総売上表示は行わない。
